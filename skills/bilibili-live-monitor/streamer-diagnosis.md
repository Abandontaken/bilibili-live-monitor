# B 站直播间诊断与改进（Streamer Diagnosis）

## 元数据

- **类型**：Workflow
- **适用场景**：基于已采集的 B 站直播音视频转写、弹幕与礼物流水，对单个主播（尤其是中小体量虚拟歌势或杂谈房）做数据化诊断，定位留存与变现瓶颈并产出可验证的改进方案
- **前置依赖**：[数据库解析与口径防坑指南](data-interpretation.md)（数仓表结构与八大口径规则）、[跨房全局身份消解数仓](warehouse.md)（`bili-live warehouse sync`）
- **最后更新**：2026-11-20

## 目标与边界

**目标**：用客观数据、语音-弹幕对齐切片和同体量对照基线，找出目标主播当前最拖累留存或流水的 3–5 个具体瓶颈，产出可落地、可复测的改进方案与止损清单。

**不做什么**：
- 不修改采集配置、不建房、不向源数据库或数仓写入任何记录（严格只读分析）。
- 不靠未经验证的行业鸡汤下结论：没有本房实测证据或同体量基线支撑的惯常说法（如求路人亮 0.1 元灯牌养大户、高频喊欢迎、无门槛发红包热场、收礼后长篇猛夸）一律不得作为推荐动作。
- 不在样本过少（如录制不足 3 场或有效付费人次过少）时强行下统计归因结论；样本不足时降级为「单场质性切片 + 待验证假设」。
- 不主动外发报告或联系主播；交付终点为本地诊断报告文件。

## 验收标准

任何无上下文的新 agent 读完本 skill 后，产出的诊断报告必须同时满足以下 6 条：

1. **只读与口径合规**：所有 SQL 查询以只读模式（SQLite URI `?mode=ro` + `PRAGMA query_only = ON`）读取 `live_warehouse.sqlite3`（若近期有新收尾场次，先执行一次幂等 `bili-live warehouse sync`）；严格遵守 [data-interpretation.md](data-interpretation.md) 的八大口径规则（观众真实花费一律用 `paid_milli_yuan`，财富分层一律用 `wealth_level`，同屏在线一律用 `online_count`，本房勋章一律按 `medal_ruid = dim_rooms.anchor_uid` 判定）。
2. **先定档，再对照**：开篇必须明确目标主播的**规模档位**（`<30` 舰新人小房 / `30–99` 舰腰部房 / `100+` 舰百舰大房）与**内容赛道**（歌势 / 杂谈 / 游戏），所有关键指标（时薪、沉默率、弹幕密度、PK 占时与吸金比、45 秒接话率）必须附带**同档位基线对照**，禁止脱离体量跨档硬比。
3. **证据闭环**：每条核心瓶颈判断必须同时包含：(a) 量化指标 + 样本量 `N` + 中位数或剔除单笔离群值后的稳健口径（防止偶发大礼扭曲均值）；(b) 至少 2 个带具体场次时间戳的语音-弹幕切片原文（优先取终审修订文本 `fact_transcripts.text`，并联表 `fact_cohost_intervals` 标明是否落入 PK/连麦多人混音区间）。
4. **有止损，有动作，可复测**：
   - 改进建议严格控制在 **3–5 条**，按「预期杠杆 × 落地难度」排序；每条必须写清：**当前做法 → 具体改动 → 预期改变哪个可观测指标 → 1–2 周后如何用数仓复测**。
   - 必须单独列出 **1–2 条「立刻止损项」**（明确叫停或降频已证实为负收益/低效的动作）。
5. **高价值机会具象化**：若数仓具备足够记录，必须附带「高价值沉默访客或近期流失熟客切片」（例如荣耀 ≥35 级、驻留 ≥5 分钟却零付费的访客，或近期断聊/掉舰熟客的最后互动切片），说明主播在哪个具体交互瞬间漏掉了承接机会。
6. **隐私与读者口径匹配**：默认输出**内部复盘版**（面向分析师或运营，保留场次时间戳便于定位）；若需面向主播本人沟通，可另附一版**主播可执行版**（去掉冷硬的客单价与商业术语，保留具体可操作的节奏与互动建议）；任何对外或第三方分享版本严禁包含真实观众 UID、未脱敏昵称、可反向检索的冷门长原话或本机私有路径。

## 可用资源与退化边界

- **主数据源**：`live_warehouse.sqlite3`（`v_resolved_events`、`fact_transcripts`、`fact_session_presence`、`fact_room_metrics`、`fact_cohost_intervals`、`dim_rooms`、`dim_users`）。
- **未收尾场次与原始报文**：`monitor.sqlite3`（仅在排查尚未完成终审的最新场次或核对原始协议字段时只读访问）。
- **可选扩展检查**：
  - 歌势主播怀疑「声乐稳定度或选曲」是主要瓶颈时，可结合外部音频/音准对照工具抽检 2–3 首高频翻唱曲目，区分内容硬伤与互动运营问题。
  - 若需对照同档位多房基线，直接在同一数仓 `live_warehouse.sqlite3` 中按相同规模档位与赛道聚合其他房间作为对照组。
- **退化场景**：
  - **无终审语音转写（仅有弹幕与礼物流水）**：跳过「口头客套频率 / 45 秒口头接茬 / 唱聊时长占比」诊断，在报告开头显式声明仅完成流量与账单层诊断，禁止凭弹幕脑补主播原话。
  - **录制场次 < 3 场或总付费人次 < 20**：不做跨场留存与复购因果归因，降级输出「单场质性切片 + 待补充采集的 2–3 个观测问题」。

## 诊断框架与实证先验（方法论建议）

以下 5 个维度基于千小时级 B 站中小直播间实证观察提炼，agent 应根据目标主播的实际数据表现灵活裁剪，不必机械填满全部五项：

### 1. 客群结构与收入韧性（破除「0.1 元养成漏斗」迷思）
- **实证先验**：进房约 96% 沉默白嫖是常态；`<5` 元低价试水新客超过 99% 不会顺漏斗爬升为大户，新客大额流水主要来自早已在全站习惯消费的跨房老手（荣耀 25 级以上）。中小房约七成流水由 33 万元以下的普通工薪族与学生熟客撑起，约三成来自荣耀 50 级以上塔尖玩家。
- **排查重点**：
  - 拆解本房付费角色（`<15` 元过客 / `15–499` 元未上舰听众 / 单月舰长订户 / `≥500` 元核心大哥）及 Top 1 / Top 3 流水集中度。
  - 识别**单腿依赖风险**（单一大哥断崖领先且缺乏二、三号熟客竞争，既易见顶又脆弱）。
  - 核查「进门即买舰长或百元重礼的跳级老手（荣耀 25+ 级）」在本房的次场留存与复购率。

### 2. 流量精准度与开播时段效率
- **实证先验**：在线人数与单位产值经常倒挂。泛娱乐或擦边标题拉来的高进房常是虚胖分母，精准垂类标签（如明确曲风或歌手定位）虽降低泛点击，但进房转化更高；深夜档在线人数远低于白天挂机电台档，但单名在线观众的每小时产值往往高出数倍。
- **排查重点**：对比目标主播不同开播时段（白天 / 晚间黄金档 / 午夜后）及不同标题下的 `online_count`、每小时实付流水与单位在线产值，定位「高人头低转化」的空转时段。

### 3. 破冰、接话与公屏聊天健康度
- **实证先验**：
  - **高杠杆正向动作**：未付费观众亮勋章进场或发首条弹幕后的 **45 秒内点名接上话茬**，可使荣耀 40 级以下观众随后 5 分钟掏钱概率抬升约 3 倍；500 元以上直刷重礼 1 分钟内盲刷接近 0%，超九成出手前都在轻松插科打诨。
  - **已证伪的低效或负收益动作**：
    1. **高频机械报菜名**：每小时口头喊欢迎、道谢、催关注达百余次，会把公屏正常话题切碎，反而拉低开口观众的 10 分钟留存（成熟房常以文字场控小号发谢礼，主播把口头时间留给连贯聊天）。
    2. **无门槛红包热场**：引来大量跨房自动抢包脚本与沉默号，满屏口令反而挤走正在聊天的熟客（应改用带 3 级粉丝牌或舰长门槛的免费天选时刻）。
    3. **收礼后长篇大论猛夸**：对老熟客回访率与新客后续复购均无显著正向抬升；真正决定观众下次是否回访复购的是**他当晚自己在公屏发了多少条弹幕**。
- **排查重点**：抽样评估 45 秒内接茬率、每小时口头机械客套频次、话题连续时长、公屏活人发言占比，以及发红包前后的活人弹幕变化。

### 4. 变现节奏：蓄水与收割是否错位
- **实证先验**：`<100` 舰中小歌房平时唱歌与闲聊占约 89% 时长、时薪平缓，本质是在牌桌旁留住熟客蓄水；高爆发流水（约 14 倍时薪）集中在占约 11% 时长的连麦 PK（尤其是中间 1 分钟双倍计分窗口）及 15 元盲盒点歌后的追投窗口。`100+` 舰大房则以舰长续费与醒目留言为主，不必强打 PK。
- **排查重点**：
  - 核查房间规模与变现打法是否错配（如 `<30` 舰小房照搬百舰大房佛系不打 PK、不给熟客出手理由；或熟客尚未开口聊热时硬开空转 PK）。
  - 核查 PK 频率、双倍窗口话术衔接、点歌菜单与盲盒规则清晰度。

### 5. 内容护城河与情绪消耗（按赛道选做）
- **实证先验**：歌势房中，扎实唱功与鲜明曲库是镇场与防止弹幕越界的第一道防线；单场播得过久导致后半程状态下滑，或在低客单价互动中过度消耗情绪，往往比「不会要礼物」更伤长期留存。
- **排查重点**：观察单场时长与后半程互动质量衰减、唱聊比例及公屏越界控场情况；歌势房按需抽检高频曲目稳定度。

## 已知陷阱（来自真实分析返工记录）

| 陷阱 | 表现 | 应对 |
|---|---|---|
| 盲盒面值与实付混用 | 用 `output_milli_yuan` 算客单价，开出高价礼物时人均消费严重虚高 | 衡量观众真实花费一律用 `paid_milli_yuan`；仅分析开盒盈亏刺激或对齐前端展示时用 `output_milli_yuan` |
| 原始报文重复记账 | 直接累加 `raw_events` 中的 `SEND_GIFT`+`COMBO_SEND` 或 `GUARD_BUY`+`USER_TOAST_MSG`，流水翻倍 | 所有统计一律查已完成订单去重的 `v_resolved_events` / `fact_session_presence` |
| 外房牌剥离误判 | `allows_ext_medal = 0` 的房间把 `medal_ruid IS NULL` 误判为「纯新粉/专一单推」 | 跨房属性必须跨 `room_id` 聚合 `fact_session_presence`，严禁单凭空勋章字段推断 |
| 短长房号错配 | 用 `medal_room_id = room_id` 判本房牌，把老号段短房号全判成外房牌 | 一律按 `medal_ruid = dim_rooms.anchor_uid` 判定 |
| 旁路读 raw ASR | 直接读未校正转写，把错别字（如歌名/人名误识别）当成主播口误 | 优先读 `fact_transcripts.text`（已叠加终审修订），无终审时显式标注为未校正 raw |
| PK 混音错归因 | 把 PK 对手主播或连麦观众的话算到目标主播头上 | 联表 `fact_cohost_intervals`，凡落入 `pk`/`pk_punish`/`voice_join` 窗口的转写必须标注多人混音 |
| 单笔离群值带偏诊断 | 某场恰好有 50+ 级大佬路过砸一笔大礼，把偶发运气当成常态打法 | 同时汇报中位数与剔除 Top 1 离群事件后的常规基线，单次爆发不直接归因为常态方法 |
| 凭直觉编造日历规律 | 假定「发薪日（如 10/15 号）打赏更高」并建议主播卡发薪日冲榜 | 实测控制房间与个人固定效应后发薪日无显著抬升；任何周期规律必须先在本房历史数据上验证 |

## 输出规格

输出为一份结构化 Markdown 诊断报告，存放于调用方指定目录（例如 `<output_dir>/diagnosis_<room_id>_<YYYYMMDD>.md`），包含五个固定区块：

1. **一页结论（BLUF）**：规模档位与赛道、核心健康度仪表盘（本房 vs 同档基线对照表）、最紧迫的 1 个核心矛盾。
2. **数据快照与客群拆解**：覆盖场次/时长/样本边界、付费角色四分表、Top 集中度与单腿风险评估、开播时段产值对比。
3. **关键瓶颈证据（3–5 项）**：每项包含「量化指标 + 同档对比 + 至少 2 条带时间戳的语音/弹幕切片」。
4. **高价值机会清单**：近期沉默高荣耀访客或流失熟客的漏接切片（内部版留时间锚点，外部版全脱敏）。
5. **行动计划与止损清单**：
   - **立刻止损（1–2 条）**；
   - **优先改进（3–5 条）**：按表格列出「当前做法 / 具体改动 / 预期改动指标 / 1–2 周复测方式」。
   - （可选）若用户需要发给主播本人，文末附一节温和、无商业黑话的「给主播的 3 条可执行建议」。
