# 歌词整理

本文件由根 `SKILL.md` 按需加载，不单独注册。当前工作库地址不在公开文件中写死。

本 skill 的终点是**一首歌一份可追溯的结构化提案**。worker 只交提案。主线程逐首质检通过后，由唯一写入者合并。整理对象是真实歌曲档案与经模型逐首阅读审查的歌词，不是网页抓取汇总或正则质量标签。

## 目标与职责边界

一份合格的单曲提案必须让验收者只凭提案、所引原文，以及输入里已经有的出场记录，就能回答：
- 稳定的作品身份（`work_id`）是什么，属于哪个版本（`version_id`）与哪种语言（`language`）。
- 原唱或该版本演唱者是谁（`artist_roles`）；直播主播出场关系（`appearance`）是什么。
- 词、曲、专辑、发行日期等非空元数据各自来自哪份原文的哪个位置（`field_sources`）。
- 歌词原文逐行是什么（`verbatim_lines`），展示行是什么（`lines`），做过哪些展示转换（`transforms`），每一行的来源哈希和逐字 quote 是什么（`locators`），原有顺序与重复副歌是否完整保留。
- 完整度结论（`completeness`）的依据是什么，缺了哪一段、存在什么来源冲突（`conflicts`）或信息缺口（`gaps`）。
- 哪个模型在何时通过逐首阅读完成了审查（`review`、`input_hash`）。

### 资源与写入边界
- **可用资源**：调用方放入本次任务的该首原文、已保存的公开页、调用方授权目录、Firecrawl skill 公开搜索。
- **禁止触碰**：不得直接写入共享 SQLite、overlay 或生产场次；不得修改 `verified_songs.json`；本 skill 不启动批量、不接入生产、不发布、不跑终审、不外发、不提交 git，也不访问未授权目录；不得用模型记忆补全歌词或元数据。
- **合并权归属**：worker 只提交提案，不写共享 SQLite、overlay 或其他 worker 的产物。主线程逐首读提案和定位到的原文做质检，不能用抽查或字段齐全代替。通过后只由唯一写入者合并：核对基线与提案哈希，幂等更新，冲突不覆盖已审核知识，写完读回。未质检不得入库。重建原始导入不得覆盖已审核记录。按行去重、按行数标完整，或先删知识层再重建的旧入口，都不是这条合并路径。本 skill 不假设已经有批量导入命令。
- **行号会失效**：清洗改变分行或顺序后，旧的「第几行」不再有效。案例、检索说明和页面引用必须按新正文重算，不能继续展示失效行号。
- **转写检索边界**：短转写检索只返回候选歌曲与行号，不代替听辨，且严禁把歌词库里的字反写回转写记录。行号以当次读回的正文为准。

## 禁止项（真实失败硬边界）

以下失败均真实发生过，作为不可越过的硬边界执行：

1. **禁止混入同页非歌词内容或漏采页面已有元数据**：如《红玫瑰》混入 KKBOX 同页专辑曲目《烟味》《淘汰》，且漏掉页面已写明的作曲梁翘柏。网页标题、按钮、导航、推荐标题、专辑曲目表一律不得留在歌词行，页面已写明的词曲等字段不得漏采。
2. **禁止混入百科与评论区噪声**：如《暗香》混入评论邮箱与参考文献。百科赏析、评论框、联系邮箱、参考文献一律不得进入歌词行。
3. **禁止无依据粘连或自行断句**：如《如愿》首行两句粘连。同页或另一来源已有确切词句能分开时，应恢复断行，不要求原文该处本来就有空格或换行。恢复时不得新增、删除或改写唱词，也不得为了好看自行断句。没有确切依据时保持原样，并在 `gaps` 记下粘连。
4. **禁止按行去重丢掉重复副歌**：歌曲本身的重复副歌与原有段落顺序必须完整保留，不得用行级去重删除重复唱段（整页重复抓取的冗余块除外，但需区分整页重复与歌内重复副歌）。
5. **禁止用行数推断完整度**：行数多少不能证明全文完整。不得因「行数够」标为 `full`；凡存在截断或段落缺失必须标为 `partial`，并在 `missing` 中写明缺失段落或截断位置。
6. **禁止将抓取或规则抽取冒充 AI 审阅**：Firecrawl 抓取、regex 切分、按短行抽取、按站点打分选页都不是 AI 审阅。方法名、抓取记录或字段表面齐全均不能代替模型逐首阅读原文，机器 schema 校验、行号连续检查与引用定位检查只能过滤明显不合格提案，不能代替逐首阅读。
7. **禁止跨版本、跨歌手或跨语种拼接凑完整**：不得把不同版本、不同演唱者、译文、罗马音与原词拼成同一首歌词。来源不足或相互矛盾时标明 `gaps` 或 `conflicts`。已经读清的版本仍要分别交提案，不能用一个空的 `ambiguous` 代替加工。
8. **场次未知不能挡住已有歌词**：《Weight of the World》同时有英文原词、日文原词「壊レタ世界ノ歌」和中文意译。当次模型 `xai/grok-4.7` 因标题没有语言限定，把提案写成 `ambiguous` 且 `lines` 为空。英文已从 “I feel like I'm losing hope” 读到 “Come to life”，日文已从「消えゆく救い」读到「僕は」。作品、语言或录音版本、场次识别是三层。这场唱哪一版未知，只记在场次层；有证据的英文版和日文版分别交提案。两套原词不是译文关系，不能互拼，中文意译也不入原词行。
9. **同页两种格式不是歌内重复**：《牵丝戏》同页 LRC 和 TXT 是同一正文抓了两次，正文只取一套。末五句在 02:59 和 03:22 又唱了一遍，这是歌内重复，选定的那一套里必须保留：「风雪依稀秋白发尾」「灯火葳蕤 揉皱你眼眉」「假如你舍一滴泪」「假如老去我能陪」「烟波里成灰 也去得完美」。
10. **名字出现不足以推定角色**：单独的「排骨教主」名字链接只证明这个名字出现，不能标 `cover`。当次主线程改用百科翻唱表整行：「2016年05月20日 | 排骨教主 | 《牵丝戏》 | 昌禾文化」。英文和日文《Weight of the World》同样把孤立艺人名换成带字段名的整段：演唱者 quote 含 `Vocals`，角色只收窄为 `version_vocalist`；日文词、曲 quote 分别含 `Lyricist`、`Composer`。作词、作曲和演唱者也一样，不能凭名字出现写成原唱或该字段角色。
11. **现页身份不是旧片段归属**：《西江月》的 QQ URL 现指向李毅恩 Lye 的 2026 单曲，现页身份可以核实。旧三行残句和直播场次与这版录音的归属没有证据。URL 现目标身份已核实，不等于旧歌词片段或场次作品已确认。候选 metadata 只记在该链接目标上，不得改挂场次。

## 身份、语言与元数据规则

- **作品、版本、场次分开**：同名不自动合并。作品身份、语言或录音版本、这场唱的是哪一版，分开记。场次未识别时，不猜测主播唱了哪一版，也不因此扣下已经读清的版本歌词。译词、罗马音、多语版本各自用 `version_id` 与 `language`，不得混入原词 `lines`。翻唱不机械拆成新 `work_id`，除非证据表明歌词或作品身份不同。演唱者、作词、作曲和翻唱的 quote 都要带上角色关系，不能只是人名；角色只写 quote 支持的宽度，例如 `Vocals` 字段只支持 `version_vocalist`，不能升成原唱。
- **主播与歌手分离**：不得把翻唱者写成原唱，更不得把直播主播写进 `artist_roles` 充当原唱或版本演唱者。主播出场只放 `appearance`，严格沿用已有记录中的「现场」「播放」或「不确定」；转写标为播放的记录绝不能写成现场亲唱。输入无出场记录时省略或置空，worker 不猜测主播与歌曲的关系。
- **元数据逐字段溯源**：词、曲、专辑、发行日期、语言只填写来源明确写出的内容，每个非空字段必须在 `field_sources` 中给出 `source_id` 与具体定位（如精确 quote）。来源未写明的一律留空（`null`），不编造、不用记忆补齐。

## 审阅与检索建议

- **原文优先与公开检索**：优先使用输入已有的原文。旧提取文本只作定位提示，不能代替来源里的逐字 quote。缺页时才按 Firecrawl skill 公开搜索，使用已有命令 `python -m firecrawl_skill search`，并显式加上 `--max-results 6`；正文保持该 skill 的 markdown 默认，不要另造参数。一次只做有目的的少量补源，仍不足就写明缺口并停，由主线程决定是否继续。搜索不是已审，提案要记下实际查询和结果标识。不得把 ASR 私人信息、UID、整段私有转写或主播私聊发到搜索。Firecrawl 配额用尽时按该 skill 回退，不改用未授权抓取冒充已审。没有歌词页、工具失败或搜索无结果，标 `unresolved` 或 `partial` 并写明缺口，停止补写。
- **正文不能被压缩掉**：任务包长到放不下歌词时，拆开再审。不能删掉重复副歌，也不能只送前半首还声称看过全文。
- **上下文隔离**：模型必须逐首阅读原文。脏页、百科全文、带专辑曲目表的页面每次上下文只放一首歌的原文，不得多首混塞。时间戳歌词或已分行的干净歌词可在一个审阅上下文中处理少数几首，但每首仍须独立判断、独立产出提案，不得以「这几首已审」批量交差。
- **优先级建议**：建议优先审理跨房间重复出现、以及下游任务实际会命中的歌曲。

## 提案协议（输出契约）

一首歌产出一份 JSON 提案。以下是公开提案协议，不是已有 CLI，也不表示当前存储、SQLite 或本地批次已经实现这些字段。`implemented` 必须保持 `false`。本地批次若字段不同，调用方提供显式、带版本号的协议映射，说明本地字段如何对应本协议；没有映射，不要把本地文件当成已经落地的 schema，也不要另造同义字段。示例域名并非真实来源。

- `work_id`：稳定作品身份，不用标题当唯一键。
- `version_id`、`language`：版本与语言标识。
- `artist_roles`：原唱、合作或翻唱，不含直播主播。角色用来源能支持的叫法，不另造固定枚举。
- `appearance`：可选。仅在输入已有主播出场记录时原样携带（含现场/播放/不确定）。
- `lyricist`、`composer`、`album`、`released` 及 `field_sources`：非空元数据字段必须在 `field_sources` 中指向具体来源定位；未知填 `null`。
- `verbatim_lines`、`lines`、`transforms`：`verbatim_lines` 为与 `lines` 逐行对齐的所引原文行；`lines` 为审后展示行（保留重复副歌与顺序）；简繁转换、时间戳剥离、依据某来源确切词句恢复断行等操作必须记入 `transforms`，不得只留转换后文本。
- `locators`：每一行都必须同时有来源 `source_hash` 和该行在该来源中的逐字 `quote`。`result_index` 或片段位置可以附加，不能代替这两个字段。quote 必须能在对应哈希的来源里原样找到，不能是转述。断行若依据另一来源，该行的哈希和 quote 指向那个来源。
- `completeness`：`status` 取 `full`、`partial` 或 `unresolved`；`reason` 写明判断依据；`partial` 的 `missing` 必须指明缺失段落或截断处。
- `conflicts`、`gaps`、`dropped`：来源冲突、信息缺口（如未拆粘连、字段冲突）、已剔除的噪声类别（无需逐条抄录网页导航）。
- `review`、`input_hash`：实际模型名、日期、审阅方法（必须是逐首阅读原文，严禁出现 `firecrawl`、`regex`、`auto`）及输入材料哈希（若经搜索，在 `sources` 中附带实际查询词与结果序号）。

```json
{
  "protocol": "lyric_review_proposal",
  "implemented": false,
  "work_id": "work_example",
  "version_id": "original_zh",
  "language": "zh",
  "title": "示例歌名",
  "artist_roles": [{"name": "示例原唱", "role": "original"}],
  "lyricist": "示例词作者",
  "composer": "示例曲作者",
  "album": "示例专辑",
  "released": null,
  "field_sources": {
    "lyricist": {"source_id": "s1", "locator": "quote:作词 示例词作者"},
    "composer": {"source_id": "s1", "locator": "quote:作曲 示例曲作者"},
    "album": {"source_id": "s1", "locator": "quote:专辑 示例专辑"}
  },
  "verbatim_lines": ["示例第一行", "示例第二行", "示例第一行"],
  "lines": ["示例第一行", "示例第二行", "示例第一行"],
  "transforms": [],
  "locators": [
    {"line": 0, "source_id": "s1", "source_hash": "sha256:example", "result_index": 0, "quote": "示例第一行"},
    {"line": 1, "source_id": "s1", "source_hash": "sha256:example", "result_index": 0, "quote": "示例第二行"},
    {"line": 2, "source_id": "s1", "source_hash": "sha256:example", "result_index": 0, "quote": "示例第一行"}
  ],
  "completeness": {"status": "partial", "reason": "副歌后的一段在所引页面被截断", "missing": ["副歌之后"]},
  "conflicts": [],
  "gaps": ["发行日期两源不一致，未采用"],
  "dropped": ["专辑曲目", "评论框"],
  "sources": [
    {"source_id": "s1", "url": "https://example.invalid/song", "query": "示例歌名 歌词", "result_index": 0, "note": "歌词页，示例域名不是真实来源"}
  ],
  "review": {"model": "实际模型名", "date": "YYYY-MM-DD", "method": "逐首阅读原文"},
  "input_hash": "sha256:example"
}
```

示例中首尾重复行代表保留重复副歌，并非笔误。这个例子没有做展示转换，所以 `transforms` 为空，三行原文和展示行相同。真有简繁转换、时间戳剥离或断行恢复时才写入 `transforms`，且转换后仍不得出现原文没有的唱词。`"implemented": false` 必须保留，表明该结构是待验收提案协议而非已落地存储格式。

## 验收标准

另一个未参与整理过程的 agent，核对歌词和元数据时只看提案与所引原文；核对接场关系时再看输入里已有的出场记录。是否写入共享库，要看实际写入，不能只看提案自称没写。须能核对：

- **逐行可回溯且无篡改**：`lines` 的每一行都有 `source_hash` 和逐字 `quote`，并能在该哈希对应的来源里找到原句。缺哈希或缺逐行 quote 的提案不合格。唱词不得新增、删除或改写。展示行和原文行的差异只能是 `transforms` 里记下的非唱词处理，例如简繁转换、剥离时间戳，或按另一来源的确切词句恢复断行。
- **噪声彻底清除**：专辑曲目表、网页标题、按钮、导航、推荐标题、百科赏析、联系邮箱、评论框、参考文献未出现在 `lines` 或 `verbatim_lines` 中。
- **结构与重复副歌保留**：歌曲原有的段落顺序与重复副歌完整保留。按行去重丢掉副歌是不合格。把重复行当成错误的机器校验本身就是错的。
- **元数据来源可核**：所有非空元数据字段在 `field_sources` 中均有可定位的字段级来源；原文未记载的字段为 `null`。
- **角色与出场关系清晰**：`artist_roles` 只含原唱、合作或翻唱，直播主播未混入其中；`appearance` 未把转写中的「播放」篡改为「现场亲唱」。
- **版本与语种隔离**：译文、罗马音或不同版本歌词未混入原词 `lines`，未发生跨版本拼接。场次未识别时，已读清的版本仍各自有正文，不是一份空的 `ambiguous`。同页多格式只留一套，歌内按时间重复的句子仍在。演唱、作词、作曲和翻唱的 quote 都写出角色关系，不是单独人名。现页 URL 身份已核实，没有据此把候选 metadata 改挂到场次，也没有把旧残句当成该录音的歌词。
- **完整度证据充分**：`completeness.reason` 有原文依据支撑；`partial` 明确列出了 `missing` 缺失范围；不存在任何凭行数推断出的 `full`。
- **真实逐首阅读**：`review.method` 为逐首阅读原文，不含 `firecrawl`、`regex`、`auto` 等抓取或规则标签。
- **存储边界合规**：worker 只交了提案，没有写共享库。主线程已逐首质检，然后才由唯一写入者写入。重建原始导入不会覆盖已审核档案。清洗后的行号引用已按新正文重算。

歌词有缺口或被截断时，`completeness.status` 只能是 `partial` 或 `unresolved`，并写明缺什么；不得因行数标 `full`。逐行对不上、新增了唱词、把抓取或规则当成已审，或 worker 写了共享库，都是不合格提案，退回重做，不能改标成 `partial` 就算通过。
